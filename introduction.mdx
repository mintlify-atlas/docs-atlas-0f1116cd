Bookmarks is a Next.js 14 application that gives every visitor in a group the same live view of a curated link collection. Rather than each person maintaining a private browser bookmark folder that quickly goes stale, Bookmarks stores everything in a single Upstash Redis key and streams the current state to every connected client — so when one person adds a link or pins a folder, everyone sees it instantly.

## How It Works

The architecture is intentionally minimal. A Next.js frontend communicates with a single API route — `GET /api/bookmarks` to read the collection and `POST /api/bookmarks` with an `action` field to mutate it. All state lives in one Redis key, `bookmarks:shared`, which holds the full `BookmarksData` object: an array of folders (each containing links), an activity log, and a settings block.

<Note>
  Before every write, the previous snapshot is automatically saved to `bookmarks:shared:prev`, giving you a simple one-step undo layer. The store also refuses to replace real data with the built-in seed if it detects the seed looks smaller than what is already saved.
</Note>

## User Roles

Bookmarks has two tiers of access, distinguished by whether a valid admin password is supplied on write actions:

| Role | Capabilities |
|------|-------------|
| **Regular user** | Browse all folders and links, add new links and folders, toggle favorites, track clicks |
| **Admin** | Everything above, plus edit/delete links and folders, move links between folders, import and export data, reset to defaults, set the announcement banner |

The admin password is set via the `ADMIN_PASSWORD` environment variable (alias: `BOOKMARKS_ADMIN_PASSWORD`). If neither variable is set, admin actions are unrestricted — useful for local development, but always configure a password before going public.

## Data Safety Guard

The store contains an intentional safety check: if Redis already holds a collection that is larger than the default seed data (`hubs`, `proxies`, `helios-gust` folders), the application will refuse to overwrite it with that seed. This prevents an accidental reset — for example, if a deployment re-runs initialization logic — from silently wiping a populated collection.

<Tip>
  To deliberately reset the collection to the default seed, use the **Reset** action in the Admin panel. That path bypasses the guard because it is an explicit, authenticated request.
</Tip>
